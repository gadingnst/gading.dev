In the previous post ([Part 2](/blog/building-agent-memory-free-vendor)), I went on at length about *Hybrid Scoring* and *1-Hop Related Dates Expansion* to simplify memory relationships for my AI assistant, **Nouva**. On paper, it all looked great.

Then I actually built it in my homelab, and realized AnythingLLM wasn't pulling its weight.

So I took AnythingLLM out of my memory architecture and built a lean **Nouva Memory Engine** with **FastMCP (Python)**. It talks directly to Postgres + `pgvector`, plus ordinary relational tables for deterministic analytics.

Here's the architecture and how the implementation went.

---

### The new architecture: a Dual-Lane Memory Engine

Before the code, here's the overall flow of Nouva's new memory:

![Nouva Memory Engine Architecture](/media/blog/membangun-agent-memory-part-3/diagram.svg)

The core idea is splitting the search path by the type of question (Dual-Lane). The semantic path (RAG) and the quantitative path (SQL) can't be mixed if you want accurate answers and low token use.

Memory data lives in one of two states:
1. **Active Memory (local)**: data that's in progress or from today (the day's active chat transcripts and unfinished daily notes). It's written straight to my agent server (`active_memory_dir`) so writes are fast.
2. **Archived Memory (NAS)**: after a *grace period* (e.g. H-1), the pipeline moves finished data (raw transcripts, daily summaries and indexes) to separate storage on the NAS (`archived_memory_dir`), permanently and read-only. That keeps the agent server's SSD free.

---

### 1. Retiring AnythingLLM and moving to FastMCP

At first AnythingLLM felt very useful, because it gave me an instant API for managing documents and a vector database. Thinking about it more, though, it was *bloated* for a personal assistant in a homelab. It used a fair amount of RAM and CPU on my K3s cluster, and all I needed was to:
1. Store markdown documents (`MEMORY.md`, daily indexes).
2. Get their embedding vectors.
3. Run cosine distance queries.

So I decommissioned AnythingLLM for good. I stopped its containers, deleted its volumes on the server and removed its ingress routing from the Kubernetes manifests.

In its place I built a **Unified Memory Engine** on **FastMCP (Python)**. Why MCP (Model Context Protocol)? It's now an industry standard supported by many AI agent clients (OpenClaw, Cursor, Zed, etc.). Build the MCP server once and you can plug this memory into your code editor, a Telegram assistant or any CLI agent, without writing a new API wrapper.

### 2. From Zed Editor straight to the server (the memory lifecycle)

How does an interaction become a memory? It starts right in the coding workspace or the day's chats.

Say I'm coding in **Zed Editor** and ask the AI assistant to save an important discussion. The assistant calls the `session_write` tool (a FastMCP tool). It records the conversation, packs it into structured JSON and saves it as a raw Markdown transcript on my agent server:

![Saving Discussion Session from Zed Editor](/media/blog/membangun-agent-memory-part-3/store.png)

The new transcript file (`2026-07-19-1037.md`) sits on my agent server (`agent-host` in Proxmox) and is linked to its parent day right away (`Parent Day: [[2026-07-19]]`):

![Transcript Saved on Agent Server](/media/blog/membangun-agent-memory-part-3/memory-md.png)

These raw transcripts stay in active storage (the agent server, not the NAS) for the H-1 grace period on purpose. After that, the daily sync pipeline ingests them, summarizes them, indexes them semantically and archives them to the NAS for good.

### 3. Dual-Lane Memory: semantic RAG vs deterministic SQL analytics

The biggest mistake people make when building RAG is forcing semantic search onto quantitative questions.

Say you ask the AI: *"What percentage of my days were productive this July?"*

With plain semantic RAG, the LLM looks for documents that are cosine-similar to "July productivity". It pulls 2 or 3 random daily summaries and tries to "make up" a percentage from that small sample. The answer will **be wrong or nonsense.**

To fix that, I split memory processing into two lanes (*Dual-Lane*).

#### Lane 1: Semantic Recall (pgvector)
This is the usual RAG path. Data from the main markdown files (`MEMORY.md`, `MEMORY_INDEX.md`) is chunked, embedded locally with the `bge-m3` model, and stored in the `memory_vectors` table in PostgreSQL with the `pgvector` extension.
*   **For:** context questions, e.g. *"How was the server boot order set up yesterday?"* or *"What was my agreement with Kak Rina regarding sahur reminders?"*

#### Lane 2: Deterministic Analytics (Postgres SQL)
Every time the daily sync script (`auto_sync.py`) runs, it doesn't only write a markdown summary. It also parses the summary's YAML frontmatter (`mood`, `importance`, `projects`, `technologies`, `date`) and stores it as SQL rows in the `daily_summaries` table in PostgreSQL.
*   **For:** aggregate or trend questions, answered deterministically, e.g. *"How many times did I code in Next.js this month?"* or *"What percentage of my days were productive in June?"*

Why Postgres? Because every developer's spiritual journey ends in the same place: **Just Use Postgres.**

![Just Use Postgres Meme](/media/blog/membangun-agent-memory-part-3/just-use-postgres.jpg)

Instead of deploying a dedicated time-series database, some exotic graph database or a separate document store just to keep personal summaries, Postgres with `pgvector` (Lane 1) and ordinary relational tables (Lane 2) handles all of it on its own.

When the assistant gets a quantitative question, it doesn't run a vector search. It turns the query into structured parameters (e.g. `start_date="2026-07-01", end_date="2026-07-19", intent="mood_timeseries"`) through the `memory_analyze` MCP tool, then runs a SQL aggregation query directly against the database.

So the AI can recall things semantically, and it can also compute aggregates and trends with 100% precision, like an analytics database:

![Mood and Productivity Analysis Using SQL Lane](/media/blog/membangun-agent-memory-part-3/memory-analyze.png)

The numbers above come purely from SQL aggregation queries. They're fast and accurate, and no LLM tokens are spent reading hundreds of lines of chat transcript.

### 4. Data structure: an Implicit Temporal Graph

You might be wondering: *"Without a physical graph database like Neo4j, how do you connect memories that continue across days (temporal relationships)?"*

The time graph is simulated implicitly (an **Implicit Temporal Graph**) directly on flat Markdown and plain PostgreSQL.

The structure looks like this:
*   **Node**: a unique date entity (e.g. the daily document `2026-07-08`).
*   **Edge**: the `related_dates` array inside the summary's YAML metadata.

Here's Nouva's memory graph view, generated automatically in Obsidian:

![Obsidian Memory Graph View](/media/blog/membangun-agent-memory-part-3/obsidian-graph.png)

For a real example, here's a snippet of YAML metadata from a `.summary.md` file stored on the NAS:

```yaml
schema_version: 1
date: 2026-06-24
people:
- Gading
- Kak Rina
projects:
- Homelab
tags:
- anythingllm-migration
- proxmox-config
technologies:
- Docker
- Terraform
- PostgreSQL
importance: 7
mood: reflective
related_dates:
- '2026-06-23'
- '2026-06-28'
```

Logically it's a temporal graph, since it links entities and documents across dates. Physically it's stored as ordinary relational data.

The data has a few properties that keep it cheap:
1. **Immutable historical logs**: daily data past the grace period (H-1) is read-only and lives on the NAS.
2. **Declarative relationships**: links between days are declared programmatically during sync, not computed at query time.
3. **Decayed traversal**: during semantic search (RAG), the query engine does a *1-hop expansion* to the dates in `related_dates` and cuts their semantic score by 30% with a decay formula:

   $$S_{\text{decayed}} = S_{\text{parent}} \times 0.7$$

   $S_{\text{parent}}$ is the original semantic score of the parent date that RAG found. The cut marks the expanded date as secondary, supporting context.

This gives you the benefits of graph/temporal traversal without the resource cost and complexity of a physical graph database.

---

### 5. The sync pipeline (`auto_sync.py`)

How does all this stay in sync? A background cron job (`auto_sync.py`) runs every day:

1.  **Reconcile & summarize:** read the previous day's raw chat transcripts still active on the local host, and have a local LLM write a short `.summary.md` with structured YAML frontmatter.
2.  **Archive to NAS:** move the original raw transcripts to NAS subfolders (`daily_sessions/YYYY-MM-DD/`) so the assistant host's SSD stays free.
3.  **Database sync:**
    *   Read the YAML frontmatter of the new summary and insert it into the `daily_summaries` table in PostgreSQL (Lane 2).
    *   Update `MEMORY_INDEX.md`, chunk it, embed it and update the `memory_vectors` table (Lane 1).

---

### Where it landed

Moving to a FastMCP-based **Unified Memory Engine** and splitting memory search into **Dual-Lane (Semantic vs. SQL Analytics)** cut my homelab's resource use noticeably. The biggest win is portability: I now have a standard memory service of my own that any MCP-capable agent can plug into.

With this setup, my assistant doesn't only "remember" past conversations semantically (chat history recall). It can also analyze, aggregate structured data precisely, and track my habits, productivity and day-to-day technical problems accurately.
