In my previous post, [How I Build Agent Memory Free from Vendor Lock-in](/blog/how-i-handle-agent-memory-for-personal-ai-assistant), I showed off the Two-Tier Hybrid RAG + NAS Markdown setup I built for my AI assistant, **Nouva**. When I first deployed it, it felt great. Simple, portable, not overkill.

But this is software engineering, and nothing is "done once and perfect forever". After a few weeks of running it, I hit reality again. Three new problems had me scratching my head:

1.  **Index bloat:** the flat `MEMORY_INDEX.md` grew too fast. It held a cumulative list of daily topics since the beginning of time, so it got heavier every day. AnythingLLM's RAG started struggling, and semantic search accuracy dropped because of all the noise.
2.  **Vector dilution:** semantic scores from the vector database were often too close between dates. The AI would mix up a serious server architecture discussion from last week with a casual chat on another day, just because of a keyword that happened to overlap.
3.  **Unbounded graph traversal:** when I tried linking threaded chats (`continue_of` / `related_dates`), without a limit it could pull dozens of markdown files from the NAS at once. Painfully slow!

So yesterday I decided to do a big refactor of Nouva's memory system. The fix: **Two-Tier Hierarchical Summary & Hybrid Scoring**.

---

### The architecture, before vs after

To make it easier to picture, here's Nouva's memory flow before and after the rework.

#### 1. Before
In the original setup, semantic search went straight to the flat, ever-growing `MEMORY_INDEX.md`, then fetched raw transcripts from the NAS with no re-ranking.

![Architecture Before](/media/blog/membangun-agent-memory-bebas-vendor/architecture-before.png)

#### 2. After
In the new setup, a **Hybrid Scoring** layer (Semantic + Importance + Recency) filters candidate dates before anything is fetched from the NAS. The sync process also gets a **Reconciliation Pass** and **Daily Summary Generation**, so the data stays tidy and properly indexed.

![Architecture After](/media/blog/membangun-agent-memory-bebas-vendor/architecture-after.png)

Now the changes, one at a time.

---

### 1. Fighting bloat with daily summaries & YAML frontmatter

Before, raw daily notes were the only memory data in RAG. Now, before those notes are archived to the NAS, the `auto-sync.py` script calls an LLM to generate a new file: `memory/summaries/YYYY-MM-DD.summary.md`.

The summary file is very clean and comes with structured YAML frontmatter:

```yaml
---
schema_version: 1
date: 2026-07-06
people: [Gading, Rina, Freedy]
projects: [Nouverse Core, Homelab]
tags: [Kubernetes, Docker, RAG]
importance: 7
mood: excited
related_dates: [2026-07-01]
uncategorized:
  technologies: [Pydantic]
  projects: []
---
### Today's Summary
- Completed the refactor of Nouva's agent memory with the hybrid scoring scheme.
- Discussed K3s cluster worker nodes setup with Freedy.
```

*   **Controlled vocabulary:** the `projects` and `technologies` fields have to match a fixed list in `memory_config.json`. The `libraries` category (React, Next.js, LangChain and so on) is now merged into `technologies` to keep the metadata compact. If a new term shows up (like a library or technology such as `Pydantic` that isn't registered yet), the LLM puts it under the nested `uncategorized` object so the main vocabulary stays clean.

    You might ask, *"Why hardcode the controlled vocabulary and weights in `memory_config.json`?"* Simple: so far this memory system is only for my personal use. At personal scale, a static config re-read on every run (per invocation) is more than enough, safe, and doesn't need a dynamic database layer or an annoying hot-reload service.
*   **Idempotency & reconciliation:** I added a `reconcile_missing_summaries()` step. If the LLM proxy timed out or errored halfway yesterday, the next cron run scans for missing summaries and regenerates them. No more *silent data loss*.

### 2. Hybrid scoring: balancing semantics, importance and time

If you rely only on RAG's semantic score, important old data gets buried under unimportant new data. And fresh casual chat often floats to the top.

To fix that, I put a **Hybrid Scoring** formula in `query-memory.py`:

$$\text{Final Score} = (w_{\text{semantic}} \times S_{\text{semantic}}) + (w_{\text{importance}} \times S_{\text{importance}}) + (w_{\text{recency}} \times e^{-c \times \text{days}})$$

The weights live in `memory_config.json`:
*   **Semantic (50%):** the raw similarity score from AnythingLLM's vector database.
*   **Importance (30%):** a 1-10 scale from the YAML metadata (architecture migration notes get 8-10, waifu chat gets 1-3).
*   **Recency decay (20%):** exponential time decay. Newer notes score higher automatically.

With this, an important discussion from 3 months ago (high importance) won't lose to last night's skincare reminder (low importance).

### 3. Keep it simple: BFS traversal replaced by programmatic 1-hop expansion

When I first designed this, I wrote a complex graph traversal using **Breadth-First Search (BFS)** with a depth limit (`max_depth = 2`) to follow links between dates. The idea was for the assistant to pull in connected chat history automatically.

After trying it, I found the recursive BFS traversal was slow and prone to **date hallucination** from the LLM (it often guessed past dates that had no logs at all).

So I reworked it into something much simpler and deterministic:
1. **Topic detection at sync time (programmatic):** during the daily sync, the Python script scans the new summary's metadata and matches it against keywords in the local `MEMORY_INDEX.md`. The top 2 most relevant dates go into the YAML `related_dates`. That costs *zero* LLM tokens, and the dates are guaranteed 100% valid.
2. **1-hop expansion at retrieval:** when the assistant searches memory (`query-memory.py`), there's no recursive BFS anymore. It takes the candidate dates from semantic RAG and does a **1-hop** expansion to their `related_dates`, cutting their semantic score by 30% (`score * 0.7`).

I also made the output of `query-memory.py` as lean as possible with **Lazy Loading**. Instead of dumping long, token-hungry raw transcripts, the script now returns only clean summaries from the relevant `.summary.md` files, plus a dynamic `Path` to the raw transcript subfolder on the NAS (`daily_sessions/YYYY-MM-DD/`) and `Links` to related entities. The LLM reads raw transcripts *on demand*, only when it needs specific details from a conversation.

This keeps the benefit of relationships between documents (a topic graph), while the code stays light, fast and free of messy traversal bugs. *Keep it simple!*

### 4. Bonus: it works as an Obsidian vault

Because the file naming (`YYYY-MM-DD.md`) and the new summaries use standard YAML frontmatter, I got a bonus I didn't expect: **the `memory/` folder can be mounted directly as an Obsidian vault!**

I only added one line to the summary generator prompt to append wikilinks at the bottom of the markdown body:

```markdown
---
# YAML Frontmatter...
---
### Today's Summary
- [Point 1]

---
**🔗 Links:** [[Gading]] · [[Nouverse Core]]
```

Mounted in Obsidian on my laptop, I get **Graph View**, **Backlinks** and a **Calendar Heatmap** for free, without writing a single line of visualization code. RAG is happy with clean metadata, and I'm happy browsing Nouva's chat history as a nice-looking graph.

To keep the graph tidy instead of a tangled *spiderweb*, I added a few rules:
1. **No wikilinks for related dates:** relationships between dates (`related_dates`) are deliberately **not** rendered as visual wikilinks in the body. They stay in the YAML frontmatter for the AI to read programmatically. That keeps the graph free of confusing lines criss-crossing between dates.
2. **Timeline spine:** every daily note links to the previous day's note (e.g. `« [[2026-07-05]] | Timeline Spine`). That forms one straight chronological line (a spine) from left to right in the graph.
3. **Parent link:** raw chat transcripts link to their parent daily note, so sessions orbit neatly around their date node instead of floating alone as *orphans*.

### Backfill and migrating old data

The last problem was the old data already archived to the NAS before this scheme existed. To bring it in line, I wrote a one-off migration script (`backfill-nas-memories.py`) that:
1.  Scans and reads old daily notes from the NAS.
2.  Generates new `.summary.md` files through the LLM in small steps (with a `time.sleep(2)` pause so the LLM doesn't choke).
3.  Saves the summaries in the local `memory/summaries/` folder (they're tiny, so they don't weigh on local disk).
4.  Syncs all the new summaries to AnythingLLM.

So do I finally need a fancy, paid external memory stack? Still **no**. I can still get by with local markdown files, a few Python scripts and simple hybrid scoring math tuned to what I actually need, without burning LLM tokens or depending on a third-party vendor.

What this refactor showed me is that a tidy markdown folder, YAML frontmatter, a bit of hybrid scoring math and a standard markdown tool like Obsidian are enough to build an AI agent memory system that's smart, fast and 100% yours.
