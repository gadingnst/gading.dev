If you build or use coding agents with terminal access (an `exec` tool, say), you've probably seen this: the agent starts out sharp and easy to work with, and then around turn 20 or 30 it starts hallucinating, repeating itself, or fails with `context length exceeded`.

The cause is almost always messy tool I/O. The model itself is rarely the problem.

One terminal command with uncontrolled output is enough: `docker logs`, a `git diff` across a monorepo, or a build script dumping thousands of lines of stack trace. All that raw text lands in the context window. Once 4 MB to 6 MB of log goes straight into the prompt payload, the damage stacks up:
1. The context window is full right away.
2. Input tokens on every following turn balloon (so cost and latency go up).
3. The model suffers *attention drift*. Important instructions and the task context from early in the session get buried under terminal logs that nobody needed to read in full.

When I was building **[Nouride](https://nouride.com)** (a lightweight multi-agent daemon for homelab work), this was one of the first things I had to fix. I needed an agent like Nouva to pair on code for dozens or hundreds of turns without stalling halfway.

Here's what I tried, and what I ended up using: **Tool Output Spilling**.

---

### What I tried that didn't work well

Before landing on a pattern I liked, I tried a few common approaches that turned out to be painful in real use.

#### 1. A rule in the system prompt
At first I thought an instruction would do: *"If a terminal output is likely to be long, redirect it to a file and just give me the path."*

It didn't work consistently. An LLM can't know how long a program's output will be before the program runs. When it calls `journalctl` or `npm test`, it can't tell whether the result will be 5 lines or 10,000. Leaving memory management to the model's guess before the command runs is very fragile.

#### 2. Crude truncation (keep the head)
Next I put a character limit in the backend. If the output went past a threshold, cut it and keep the first 2,000 characters.

That created a new problem. In execution logs, the most important signal is almost always at the end (the *tail*): the last error line, the compiler summary, the failing exit code. Keep only the *head* and the agent sees successful setup lines, concludes everything went fine, and the process actually crashed at line 5,000.

#### 3. A "run it again if you need it" marker
Some agents just return a short note: `[output 5MB truncated, re-run command if you need the details]`.

That falls apart when the command is a build or test suite that takes 2 minutes. Should the agent wait another 2 minutes just to look at the middle lines it couldn't see?

---

### The fix: spill to the filesystem

I ended up borrowing an old idea from operating systems: **memory spilling / paging to disk**. When fast memory (RAM) is tight, the OS swaps unused pages to disk instead of killing the process.

In Nouride, the daemon harness sits between the tool's result and the prompt payload sent to the LLM. The flow is deterministic.

#### 1. Cap by turn budget
One tool result must not eat the context window. In Nouride, a single tool result gets at most **25% of the total conversation budget** (with a floor of 2,000 tokens). So if the agent calls 3 or 4 tools in one turn, there's still 50% left for the persona prompt, memory and chat history.

#### 2. Write the full output to disk
If a tool result is longer than the budget:
- The harness writes the full text atomically to disk at `$DATA_DIR/tool-output/<session_id>/<call_id>.txt`.
- The file is locked to `0600` right away (so nothing leaks if it contains logged environment variables or secrets).
- The spill folder is added to the agent's read-only sandbox paths automatically, so the agent can read the file when it needs to.

#### 3. Send a structured excerpt (head & tail)
The LLM only gets a short excerpt, split in fixed proportions:
- **Head (65%):** the start of the output, so the model sees the initialization parameters and config.
- **Tail (35%):** the end of the output, so the model reads the status summary or fatal error straight away.
- **Metadata:** the line count and original size (KB), plus how many lines in the middle were left out.
- **Pointer path:** where the file is on disk, with a hint: *"Open it with `read` and an offset, or narrow it with `grep`."*

The agent receives something like this:

```text
[output too large for the context: 14,200 lines, ~2,840KB.
The first 65 and last 35 lines are below; 14,100 in the middle are not.]
Full output: /srv/nouride/.nouride/data/tool-output/s_019/call_exec_42.txt
Open it with `read` and an offset, or narrow it with `grep`; it is a normal file and it is readable.

... (initial command output) ...

... (final summary / error output) ...
```

---

### What it changed in practice

Spilling fixed several problems at once:

1. **Error signals stay intact.** The tail is always included, so the agent sees the real failure without guessing or hallucinating.
2. **Ready to dig in any time.** If the agent needs a specific stack trace in the middle of the log, it doesn't re-run a slow command. It calls `grep` or `read` with an offset on the spill file.
3. **Context size stays stable.** Token use per turn stays lean and predictable, from turn 1 through turn 100+.
4. **Cleanup is automatic.** Spill files are managed by the chat session's timestamps. A few days after a session ends, the daemon deletes them.

---

### So

An agent you can rely on in long sessions needs disciplined I/O control in the runtime harness. Send big logs to the filesystem, and give the LLM only a structured excerpt plus a pointer to the file. The model stays on the task, and the context window doesn't fill up.
