#### Array.find()
The `find()` method searches for a value in an *array*. Now here's the difference between `find()` and `filter()`. With ***filter***, which we used before, the program keeps searching until the last *index* of the *array*. So ***filter*** collects the values it finds into a new *array*. With ***find***, on the other hand, the search stops as soon as the program gets one value. Still confused? Basically, if you're familiar with SQL, think of using the ***find*** method as adding a `LIMIT 1` to the query, while ***filter*** has no limit.

Using `find()` is actually exactly the same as `filter()`: its parameter is a *callback* function with *value* and *index* arguments. To see the difference between ***find*** and ***filter***, let's try the following case:

```js
const students = [
  {
    id: 1,
    name: 'Sutan',
    major: 'Computer Engineering'
  },
  {
    id: 2,
    name: 'Rina',
    major: 'Computer Engineering'
  },
  {
    id: 3,
    name: 'Alexander',
    major: 'Management'
  },
  {
    id: 4,
    name: 'Alexandra',
    major: 'Accounting'
  }
]

const filtering = students.filter(student =>
  student.name.toLowerCase().includes('alex')
)

const finding = students.find(student =>
  student.name.toLowerCase().includes('alex')
)

console.log(filtering)
console.log(finding)
```

From the example above, `filter()` produces a new *array of objects*, *Alexander* and *Alexandra*, while `find()` produces only one *object*, *Alexander*. Why is that? Both conditions we set look for a name containing the word *'alex'*. It happens because `find()` stops searching once it gets one matching value, while `filter()` keeps searching to the end of the *array* even after it finds a match. So ***find*** is usually used to look up *single-data* by a unique parameter, like an *id*, *email*, *username* etc., while ***filter*** is used to look up *multi-data* by a non-unique parameter.

#### Array.findIndex()
`findIndex()` is just like `find()`, but the difference is in what it *returns*: ***find*** *returns* the **value**, while ***findIndex*** *returns* the **index**. To see the difference more clearly, let's try an example like this with the ***whitelist*** data above:

```js
const find = whiteList.find(item => item.id === 4)
const findIndex = whiteList.findIndex(item => item.id === 4)

console.log(find)
console.log(findIndex)
```

#### Array.sort()
Now we get to `sort()`. ***sort*** is one of the ***higher-order functions*** in JavaScript that sorts an *array*. Its parameter is a *comparer* *callback* function whose arguments are the values to *compare*; the value *variables* are usually named `a` and `b`. Without a *callback* parameter, `sort()` can only sort strings `A-Z`. See the example below:

```js
let fruits = ['Mango', 'Apple', 'Banana', 'Orange', 'Grape']
fruits = fruits.sort()

console.log(fruits)
```

The result above is correct: the fruit names are sorted `A-Z`.
So what about numbers? Can we sort them from smallest to largest? Let's try again.

```js

amounts = amounts.sort()
```

"Wait, wait, why is the result like that? **1000** and **10000** come before **200** 😕". Well, that's just how it is, because by *default* `sort()` only sorts *string* values when there's no *comparer* *callback* parameter. So it automatically *converts* those numbers to *strings* first before sorting. No wonder the order ends up like that, because as *strings*, even **100000000** is smaller than **2** 😆.

Let's test it like this:

```js

```

```js
amounts = amounts.sort((a, b) => {
  console.log(`Log: a(${a}) > b(${b}) ? ${a > b ? 1 : -1}`)
  return a > b ? 1 : -1
})

console.log('Sorted result:', amounts)
```
<State

      let amounts = [1000, 100, 200, 10000, 6000, 200000];

      amounts = amounts.sort((a, b) => {
        document.getElementById('case7-log').innerHTML += `Log: a(${a}) > b(${b}) ? ${a > b ? 1 : -1}<br />`;

For a short explanation, just think of `a` and `b` as the values being compared. If the *return* is `1`, we put `a` on the right, after `b`. If the *return* is `-1`, we put `a` on the left, before `b`. And.. that's what the real sorted order looks like, not like what we tried earlier with `1000 < 200` 😠.

#### Wrapping up
So the benefit of using ***higher-order functions*** is that we don't have to rack our brains over the algorithm anymore, and we don't need *loops* anymore when dealing with *arrays*. We just put in the conditions we want to *return*. Let JavaScript do the rest 😆. Even so, we should at least know a bit about what actually happens in the process, so we know what we need to *return*.

Take sorting, for example: there are actually lots of sorting algorithms, *bubble*, *quick*, *insertion*, *selection* etc. And btw, I don't guarantee that using ***higher-order functions*** gets us the *best performance*, but at least compared to writing our own algorithm that ends up slower anyway, better to use ***higher-order functions***, lol. What we're looking at here isn't performance either, but practicality, usually called *best practice*. You can see that none of the code we wrote from start to finish is long or long-winded; it's all short and easy to read and explain.
