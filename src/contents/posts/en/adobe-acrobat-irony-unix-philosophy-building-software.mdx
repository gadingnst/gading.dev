A few days ago I was scrolling X and ran into a short, sharp tweet from [@Trish0x2A](https://x.com/trish0x2a/status/2103759408316752027?s=46):

> *"It's honestly embarrassing that Chrome accidentally became the best PDF viewer while Adobe spent decades making Acrobat slower and more bloated."*

![Tweet from @Trish0x2A on Chrome vs Adobe Acrobat](/media/blog/adobe-acrobat-irony-unix-philosophy-building-software/tweet-trish.jpg)

I laughed, a bit bitterly. This isn't only about Adobe. It's an old disease that most commercial software in our industry has caught at some point: feature creep.

Think about the irony. Adobe invented the PDF format in 1993. They wrote the standard and they own the ecosystem. Yet today, if you want to read a receipt or a two-page document, opening Acrobat feels like launching a rocket to Mars.

The laptop heats up, a loading screen spins, and a pile of background processes start up with it (Adobe Creative Cloud, Core Sync, IPC Broker, Genuine Service, a crash reporter). Then you get pop-ups offering cloud storage, e-signature workflows and, more recently, an AI Assistant button to summarize the PDF.

All you wanted was to read a document.

Then Google Chrome came along. The Chromium developers needed a small component so the browser could render a PDF in a tab without downloading it to the desktop first. Nothing fancy: render pages, scroll, zoom in and out, print. That's it. Without really trying, Chrome became the favorite PDF viewer of billions of people, because it opens in about 0.1 seconds.

Which raises the question: why does software that starts out good almost always end up as annoying bloatware?

---

## Why software keeps getting fatter

The developers who build bloated software don't have a ***skill issue***. Their coding is fine. The incentives are what's broken.

1. **Every quarter needs a "value-add"**  
   Tech companies are expected to keep growing, and product teams need something new to show at every quarterly review. If you tell management, *"This quarter we didn't add any new features; we made the core engine 15% more stable and lighter on memory,"* you look like you were slacking. If you say, *"We just shipped cloud storage integration, digital signatures, and an AI copilot inside the PDF reader,"* you get applause. New features read as proof of work.

2. **Fear of looking "too simple"**  
   There's a strange belief that paid software has to look complex to feel worth the money. If it's just one plain white window for reading text, the buyer (especially enterprise procurement) asks: *"Why are we paying this much for something that looks like this?"* So more buttons get forced in.

3. **No line between core features and peripheral plugins**  
   Everything gets crammed into one main binary. Text editing, image compression, form submission, OCR, cloud sync, telemetry and the AI copilot all run together in the same process space.

What you end up with is a slow, RAM-hungry, fragile monolith.

---

## The fix has been around since the 1970s: the Unix philosophy

Long before anyone argued about microservices or containers, Doug McIlroy and Ken Thompson at Bell Labs wrote down rules that still hold up:

> 1. *Make each program do one thing well.* To do a new job, build afresh rather than complicate old programs by adding new "features".  
> 2. *Expect the output of every program to become the input to another, as yet unknown, program.*  
> 3. *Write programs to handle text streams, because that is a universal interface.*

People misread this a lot, though.

Some take it to mean tiny programs with no features. Others go to the opposite extreme and split every function into dozens of *microservices* and separate processes, with bloated latency, tangled network hops and miserable debugging. That's not what it says.

Modular software doesn't need microservices, and it doesn't need to be split into separate OS processes. Inside a single monolith or a single binary, modularity means isolated responsibilities and firm interface boundaries.

If the core job is reading documents, keep the rendering pipeline clean and quiet. Don't let cloud sync, signatures or analytics run in the main loop. If a feature is peripheral, make it an optional plugin or a separate tool.

## The "scalable multi-tenant" illusion

This is where engineers most often get stuck in theory: multi-tenancy.

When most people hear "scalable" and "multi-tenant" for business or enterprise use, they picture one giant application holding thousands of tenants in one shared database. Every client lives in the same tables, separated by a `tenant_id` column and patched together with painfully complex *Row-Level Security* (RLS).

When traffic grows, this happens:
- **Lock contention:** one tenant running a heavy report slows everyone else down.
- **A huge blast radius:** one fatal bug or a corrupted database takes down every client in the company at once.
- **Compliance and privacy pain:** audit and security teams stay suspicious, because financial data or confidential legal material sits on the same disk as every other division's.

Scalable and multi-tenant don't have to mean one giant application that swallows everything.

Through the lens of the Unix philosophy and a *Shared-Nothing* architecture, the safest and sturdiest multi-tenant setup is separate instances.

Say a company has 20 teams. Instead of building a complex multi-tenant monolith inside the application, spin up 20 independent instances. One team, one container.

- Data is fully isolated at the storage level (separate files, separate volumes).
- The blast radius is zero: if team A crashes their instance, team B doesn't notice anything.
- Resources are split by cgroups and container limits in the OS, not by a leaky rate limiter in the application.

If the company later needs central management for those 20 or 100 instances, the multi-tenant logic still stays out of the core engine. Build a thin application layer on top instead (a Fleet Control Plane / Orchestrator).

That layer handles provisioning instances, pushing configuration in bulk and collecting audit logs in one place. The core application stays clean, light and focused on one job.

## Enterprise scale with fleets, not fat monoliths

This horizontal fleet pattern isn't coffee-shop theory. The most proven infrastructure software in the world works this way.

### 1. Docker Engine vs Kubernetes
Docker Engine never tried to become a complex distributed cluster. It does one thing: be a container runtime on a single local host. Build an image, run a container, expose a port. Done.

When the industry needed thousands of servers, Docker Engine wasn't turned into a giant monolith. A separate orchestration layer was built on top of it: **Kubernetes**. Docker stays slim on each worker node, and scheduling belongs to the control plane above.

### 2. Prometheus vs Thanos / Cortex
Prometheus is a single-node Time Series Database (TSDB) on purpose. No built-in clustering, no built-in distributed storage. That design is why it's so resilient: when the cluster network falls apart, it keeps scraping metrics on the local node without depending on any other server.

When enterprises needed years of retention and global queries across clusters, did Prometheus get rebuilt as a distributed database? No. Prometheus stays single-node, and **Thanos** or **Cortex** sits on top as a federation layer.

### 3. Grafana Agent vs Grafana Cloud
Grafana Agent only collects telemetry on the local host and forwards it. It doesn't render dashboards or run an alert engine. The boundary is very clear.

## How we apply this in Nouride

When I was designing [Nouride](https://nouride.com) (the multi-agent AI daemon running on our homelab and servers), the temptation to make it an *"All-in-One Multi-Tenant Enterprise AI Platform"* never went away.

I could have set up a Postgres cluster, added an external vector database like Qdrant or Milvus, built multi-tenant tables with dozens of complicated relations, and sold it as "enterprise ready".

I ruled all of that out early, in my own head. We went the Unix way:

- **The engine stays small, quiet and sovereign.**  
  Nouride is a single-binary daemon. Its main database is a local embedded SQLite file (`nouride.db`), not a separate database server. It uses about **~107 MB RAM** running 6 agents and 10 gateways (Telegram, Discord, WhatsApp) at once. With 1–2 agents on one active gateway, the baseline is around **70-something MB**.
- **Semantic search is pluggable.**  
  Semantic search through Ollama (`bge-m3`) is optional (*pluggable*), not a hard dependency in Nouride's core. If you don't need it, or you're on a modest machine without a GPU, the engine keeps running fast on native SQLite FTS keyword search, without carrying an embedding model.
- **Multi-tenancy through fleets, not a monolith.**  
  When an enterprise has many teams, we don't put tenant logic in the Nouride engine. We spin up one Nouride container per team. The DevOps team gets its own instance with terminal command access (`exec`), and the Legal team gets its own instance locked down with no shell access.
- **Orchestration lives in a layer above.**  
  Managing dozens of instances goes to a separate project: the **Fleet Control Plane**. That management dashboard handles provisioning, bulk config pushes and audit logs, and never touches the simplicity of the Nouride core.

## The discipline of saying "no" (especially in open source)

Starting software is easy. The hard part is keeping it from turning into slow junk after a few years.

[Nouride](https://nouride.com) isn't open source right now (maybe it will be later), but I think this applies everywhere. And the disease is usually worse in open source.

Count how many open source projects started as lean, elegant tools that people loved for being fast and simple, and two years later had become frustrating bloatware.

The cause is almost always the same: maintainers who can't bring themselves to say "no".

Every feature request gets accepted. Every pull request from a user who wants the software to cover their niche use case gets merged. Slowly the code grows, the dependency tree sprawls, the bug surface widens, and eventually what made the software good in the first place is lost to compromise.

So when a feature idea or a new pull request shows up, an engineer's first question shouldn't be *"Can we merge this?"* It should be:

> *"Does adding this compromise the fundamental reason this software was created?"*

Adobe Acrobat may have wandered too far into feature creep and corporate monetization. For the software we build today, closed or open source, the choice is still ours: drift into becoming a slow monster too, or turn down what isn't needed so the software stays sharp, quiet and good at its core job.
