Di tulisan gw sebelumnya, [Jebakan GraphRAG: Kenapa Gw Uninstall Neo4j dari Asisten Pribadi Gw](/id/blog/jebakan-graphrag-uninstall-neo4j), gw udah cerita panjang lebar kenapa gw mutusin buang Neo4j dan Graphitti dari stack asisten AI gw, **Nouva**. Intinya: *overkill*, nyusahin diri sendiri, dan boros token LLM cuma buat nge-traversal graph yang sebenernya nggak rumit-rumit amat buat skala personal.

Tapi abis Neo4j di-uninstall, gw kebentur masalah baru: **gimana cara ngelola memori jangka panjang (chat logs & history) Nouva biar tetap rapi dan cepet, tapi nggak bikin RAG-nya "mabok"?**

Kalau semua file chat log harian mentah (`YYYY-MM-DD-HHMM.md`) asal di-dump langsung ke vector database AnythingLLM, lu bakal masuk ke jebakan baru: **dilusi vektor & noise**.

Kali ini gw mau share cara gw ngedesain sistem memori hybrid yang simpel banget, tanpa dependency tambahan, tapi **95% udah ng-cover semua kebutuhan asisten pribadi gw**.

---

### Masalah klasik RAG: "dilusi vektor"

Pas awal-awal pindah ke RAG konvensional (AnythingLLM), gw nge-sync semua file log harian mentah ke vector database. Hasilnya berantakan.

Satu file chat log harian itu isinya campur aduk. Ada bahasan arsitektur Kubernetes, obrolan santai soal waifu Tifa di FF7 Rebirth, log error system, sampai reminder skincare titipan istri. Pas file ini di-chunk (dipecah per 1000 karakter) terus di-embed, nilai vektornya jadi terdilusi.

Efek sampingnya kocak sekaligus nyusahin. Pas gw nanya, *"Va, inget nggak diskusi kita soal ESG kemarin?"*, RAG-nya malah balikin chunk reminder skincare, gara-gara skor semantiknya kebetulan mirip di dalam database. Konteks yang gw cari malah tenggelam.

---

### Kenapa tetap NGGAK butuh mem0 atau GraphRAG?

Sebelum masuk ke solusinya, gw pertegas lagi kenapa buat skala personal gw tetap **95% nggak butuh** memory stack canggih yang ada di luar sana:

1.  **GraphRAG (99% nggak butuh):** proses indexing-nya rakus token LLM dan bikin CPU/GPU lokal teriak-teriak. Lu nggak butuh AI buat nyimpulin hubungan graf yang rumit cuma buat nyari diskusi server downtime minggu lalu.
2.  **mem0 (90% nggak butuh):** mem0 nyimpen fakta dinamis ke vector/graph database terpisah. Masalahnya, gw udah punya file `MEMORY.md` statis di workspace lokal yang isinya curated facts (spek PC, info keluarga, project aktif). File markdown ini jauh lebih gampang di-debug dan diedit manual, daripada harus nge-delete node graph yang salah tangkep di database yang tersembunyi.

Sisa 5% kebutuhan itu cuma kalau lu pengen analisis abstrak jangka panjang (misalnya, *"Tolong petain mood gw selama 1 tahun terakhir"*). Buat use case harian software engineer? Nggak kepake.

### Solusinya: Two-Tier Hybrid RAG + NAS Markdown

> **TL;DR:** RAG di sini gw bikin sebagai memory index doang. Tiap keyword yang masuk bakal balikin beberapa kandidat tanggal log harian (format YYYY-MM-DD). Memory aslinya cuma file markdown, dengan nama file = tanggal tadi. Jadi abis LLM dapet kandidat tanggal dari index, dia baru buka langsung file markdown-nya buat baca isi aslinya.

Sebagai gantinya, gw pasang arsitektur **Two-Tier Hybrid Memory** yang ngebagi tugas pencarian dengan jelas dan efisien:

```
[User Query] 
     │
     ▼
[Unified query-memory.py]
     │
     ├─► Step 1: Semantic Search (RAG via AnythingLLM)
     │           Mencari di MEMORY_INDEX.md (Peta Navigasi)
     │           Hasil: Nemu Tanggal Bahasan (e.g., 2026-06-24)
     │
     ├─► Step 2: Direct Read (NAS Zip Archive)
     │           Membaca transkrip mentah langsung dari file zip di NAS
     │
     └─► Fallback: Fast Keyword Search (Grep di NAS Zip)
                   Jika RAG ragu atau tidak menemukan hasil
```

#### Tier 1: Semantic Index Map (MEMORY_INDEX.md)
Chat log mentah yang panjang dan berisik udah nggak di-sync lagi ke vector database. Yang di-upload ke AnythingLLM cuma dua file:
1.  `MEMORY.md` (curated long-term facts).
2.  `MEMORY_INDEX.md` (peta navigasi).

File `MEMORY_INDEX.md` ini di-generate otomatis lewat script sync mingguan. Isinya cuma ringkasan singkat banget per tanggal. Contohnya:
```markdown
### 📅 Wednesday, June 24, 2026 (2026-06-24)
  - **🚀 AnythingLLM Migration & Configuration**
  - **🛠️ Proxmox & Terraform State Alignment**
  - **Discussions (Chat)**
    - tapi gw penasaran apa sih yg dikejar esg ini? apa isinya orang woke semua?
```
Karena file-nya bersih dari log error dan chat berisik, RAG bisa nge-embed ini dengan akurat pake model **`bge-m3`** secara lokal lewat Ollama di server homelab (Ryzen 7 5825U).

#### Tier 2: Raw Archive (NAS Folder)
Semua chat log mentah per sesi (`YYYY-MM-DD-HHMM.md`) otomatis dipindahin ke subfolder tanggal (`daily_sessions/YYYY-MM-DD/`) di NAS (`virtual-nas`) abis grace period H-2, terus file lokalnya dihapus biar disk agent-host nggak penuh.

#### Tier 3: The Glue (Unified Script)
Gw bikin script wrapper `query-memory.py`. Alurnya gini:
1.  Pas gw nanya *"Inget nggak bahasan ESG kita?"*, script-nya nanya ke RAG (AnythingLLM).
2.  RAG nemu yang cocok di file `MEMORY_INDEX.md`, terus balikin potongan teks yang isinya tanggal target: **`2026-06-24`**.
3.  Script-nya otomatis buka folder di NAS yang nge-cover tanggal itu, baca file `2026-06-24.md` langsung ke RAM, terus nyajiin transkrip full-nya ke AI Agent.
4.  **Parallel search:** selain pencarian semantik, script-nya juga jalanin *keyword search* cepet (grep-like) secara paralel ke semua file summary di NAS, biar kata benda yang spesifik pasti ketemu.

### Kenapa skema ini enak banget?

*   **Zero extra dependencies:** cuma modal script Python standar (`requests` & file-handling bawaan). Nggak perlu install graph database baru atau library aneh-aneh.
*   **Ramah resource:** `agent-host` gw yang cuma dapet jatah 4GB RAM di Proxmox tetap enteng, soalnya beban berat embedding model `bge-m3` dititipin ke Ollama di backend.
*   **100% portable:** formatnya cuma Markdown mentah dan struktur folder standar, jadi datanya aman dan gampang banget dipindahin kalau suatu saat gw mau migrasi asisten AI ini ke platform lain (tinggal import folder NAS ke Claude Project, kelar).
*   **Bebas vendor lock-in (jujur, gw udah capek):** banyak framework memory sekarang yang maksa lu pake cloud database mereka, API berbayar mereka, atau format proprietary yang bikin data lu kesandera. Gw udah capek dikunci di satu ekosistem. Dengan format `.md` mentah dan struktur folder standar ini, datanya 100% punya gw. Kalau besok gw mau ganti LLM provider atau migrasi dari OpenClaw ke framework lain, tinggal copy-paste folder NAS-nya, tanpa pusing mikirin kompatibilitas.
*   **Transparan & gampang di-debug:** kalau AI salah inget fakta, gw tinggal buka file `.md`-nya terus edit baris yang salah. Nggak perlu pusing nyari cara nge-wipe vector/graph database.

*Keep it simple*. Kadang solusi terbaik buat masalah AI modern bukan nambah teknologi baru yang makin kompleks, tapi balik ke dasar: file teks terstruktur dan script automasi yang presisi.

### Lesson learned: balik ke dasar

Dari eksperimen bongkar-pasang memory stack ini, ada satu pelajaran mahal: **jangan gampang silau sama teknologi yang lagi hype.**

Dunia AI sekarang cepet banget berubahnya, dan hampir tiap minggu ada library atau framework baru yang janjinya muluk-muluk (GraphRAG lah, mem0 lah, autonomous memory layer lah). Gampang banget kejebak "mabok teori" terus langsung install ini-itu, cuma karena kelihatan keren di kertas atau di timeline Threads.

Tapi sebelum install, coba tanya dulu ke diri sendiri:
*   **Beneran butuh nggak?** (Use case personal sama corporate itu beda jauh.)
*   **Paham nggak konsep dasarnya?** (Lu cuma butuh mapping tanggal dan keyword, atau beneran butuh traversal graph database yang kompleks?)

Balik ke dasar (*back to basics*) dan paham core concept dari masalah yang mau diberesin itu jauh lebih penting daripada numpuk dependency baru. Kadang solusi terbaik cuma butuh file teks terstruktur (Markdown), sedikit regex, dan script automasi sederhana yang presisi. Lebih hemat token, hemat RAM, dan nggak bikin pusing pas maintenance jangka panjang.

### Selanjutnya apa?

Skema flat RAG + NAS ini fondasi awal yang solid. Tapi begitu catatan harian numpuk sampai ratusan hari, tantangan berikutnya: gimana ngatasin *index bloating*, *vector dilution*, dan ngelakuin *graph traversal* (nyambungin chat yang bersambung antar hari) tanpa ngorbanin performa.

Di tulisan selanjutnya, **Membangun Agent Memory dengan Vendor Lock-in Resistance (Part 2)**, gw bakal bedah kelanjutan arsitektur ini: gimana sistem memori Nouva dirombak pake pendekatan *Hierarchical Summary* dan rumus *Hybrid Scoring* sederhana, biar pencarian memori tetap instan, rapi, dan pastinya tetap 100% bebas vendor lock-in.
