Di tulisan gw sebelumnya, [Bagaimana Saya Membangun Agent Memory yang Bebas Vendor Lock-in](/id/blog/bagaimana-saya-handle-agent-memory-untuk-skala-personal-ai-assistant), gw sempet pamer skema Two-Tier Hybrid RAG + NAS Markdown yang gw bikin buat asisten AI gw, **Nouva**. Pas awal di-deploy, rasanya indah banget. Simpel, portable, dan nggak overkill.

Tapi namanya juga software engineering, nggak ada solusi yang "sekali kelar langsung sempurna selamanya". Abis skema itu gw pake beberapa minggu, gw kebentur kenyataan pahit lagi. Ada tiga masalah baru yang bikin gw garuk-garuk kepala:

1.  **Index bloating:** file `MEMORY_INDEX.md` yang flat ternyata tumbuhnya kecepetan. Isinya daftar topik harian kumulatif dari awal waktu, jadi makin hari makin gemuk. Akibatnya RAG AnythingLLM mulai kewalahan, dan akurasi semantic search-nya melorot karena kebanyakan noise.
2.  **Vector dilution:** skor semantik dari vector database sering mirip-mirip antar tanggal. AI jadi gampang ketuker antara diskusi serius soal arsitektur server minggu lalu sama obrolan santai di hari lain, cuma gara-gara ada keyword yang kebetulan mirip.
3.  **Graph traversal tanpa batas:** pas gw nyoba nge-link chat yang nyambung (`continue_of` / `related_dates`), kalau nggak dibatasin, dia bisa narik puluhan file markdown sekaligus dari NAS. Lemotnya minta ampun!

Makanya kemarin gw mutusin buat refactoring gede-gedean di sistem memori Nouva. Solusinya: **Two-Tier Hierarchical Summary & Hybrid Scoring**.

### 1. Ngelawan bloat pake daily summary & YAML frontmatter

Dulu, daily notes mentah jadi satu-satunya data memori di RAG. Sekarang, sebelum daily notes itu diarsipin ke NAS, script `auto-sync.py` bakal manggil LLM buat bikin file baru: `memory/summaries/YYYY-MM-DD.summary.md`.

File summary ini bersih banget, dan dilengkapin YAML frontmatter terstruktur:

```yaml
---
schema_version: 1
date: 2026-07-06
people: [Gading, Rina, Freedy]
projects: [Nouverse Core, Homelab]
tags: [Kubernetes, Docker, RAG]
importance: 7
mood: excited
related_dates: [2026-07-01]
uncategorized:
  technologies: [Pydantic]
  projects: []
---
### Ringkasan Hari Ini
- Menyelesaikan refactoring memori agen Nouva dengan skema hybrid scoring.
- Diskusi dengan Freedy soal setup K3s cluster worker nodes.
```

*   **Controlled vocabulary:** field `projects` dan `technologies` wajib dicocokin sama daftar baku di `memory_config.json`. Kategori `libraries` (kayak React, Next.js, LangChain) sekarang digabung langsung ke `technologies` biar metadata-nya lebih ringkas. Kalau ada term baru (misalnya library/teknologi `Pydantic` yang belum kedaftar), LLM bakal masukin ke nested object `uncategorized`, biar vocabulary utamanya nggak kecampur.

    Mungkin lu nanya, *"Kenapa controlled vocabulary sama parameter bobotnya di-hardcode di file `memory_config.json`?"* Simpel aja: sejauh ini sistem memori ini masih murni buat kebutuhan personal gw. Di skala personal, konfigurasi statis yang dibaca ulang tiap run (per-invocation) udah lebih dari cukup, aman, dan nggak perlu nambah ribet pake layer database dinamis atau service hot-reload yang nyusahin.
*   **Idempotency & reconciliation:** gw nambahin langkah `reconcile_missing_summaries()`. Kalau kemarin LLM proxy-nya timeout atau error di tengah jalan, cron job berikutnya otomatis nge-scan summary mana yang bolong terus nge-generate ulang. Nggak ada lagi cerita *silent data loss*.

### 2. Hybrid scoring: nyeimbangin semantik, kepentingan, sama waktu

Kalau cuma ngandelin skor semantik RAG, data lama yang penting sering tenggelam sama data baru yang nggak penting. Sebaliknya, data baru yang isinya cuma obrolan santai malah sering naik ke atas.

Buat ngatasin ini, gw pasang rumus **Hybrid Scoring** di `query-memory.py`:

$$\text{Final Score} = (w_{\text{semantic}} \times S_{\text{semantic}}) + (w_{\text{importance}} \times S_{\text{importance}}) + (w_{\text{recency}} \times e^{-c \times \text{days}})$$

Bobotnya gw set di `memory_config.json`:
*   **Semantic (50%):** skor kemiripan asli dari vector database AnythingLLM.
*   **Importance (30%):** skala 1-10 dari YAML metadata (catatan migrasi arsitektur dapet nilai 8-10, obrolan waifu dapet 1-3).
*   **Recency decay (20%):** peluruhan waktu pake eksponensial. Catatan baru otomatis dapet nilai lebih tinggi.

Dengan skema ini, diskusi penting 3 bulan lalu (importance tinggi) nggak bakal kalah saing sama reminder skincare kemarin malam (importance rendah).

### 3. Keep it simple: BFS traversal diganti 1-hop expansion programmatik

Awalnya, pas ngerancang sistem ini, gw sempet nulis kode traversal graf yang kompleks pake algoritma **Breadth-First Search (BFS)** dengan batas kedalaman (`max_depth = 2`) buat nelusurin hubungan antar tanggal. Idenya biar asisten AI bisa narik riwayat chat yang nyambung secara otomatis.

Tapi abis dicoba, gw sadar BFS traversal rekursif ini lambat dan rawan **halusinasi tanggal** dari LLM (LLM sering asal nebak tanggal masa lalu yang sebenernya nggak ada log-nya).

Akhirnya pendekatan ini gw rombak jadi jauh lebih simpel dan deterministik:
1. **Deteksi topik pas sync (programmatik):** pas sinkronisasi harian, script Python-nya nge-scan metadata summary baru dan nyocokin sama keyword di file `MEMORY_INDEX.md` lokal secara otomatis. Top 2 tanggal yang paling relevan disuntikin ke YAML metadata `related_dates`. Ini *zero cost* token LLM, dan tanggalnya dijamin 100% valid.
2. **Ekspansi 1-hop (retrieval):** pas asisten AI nyari memori (`query-memory.py`), BFS traversal rekursif udah nggak dipake. Cukup ambil tanggal kandidat hasil RAG semantik, terus ekspansi **1-hop** ke tanggal-tanggal di `related_dates`, dengan skor semantiknya dipotong 30% (`score * 0.7`).

Selain itu, output `query-memory.py` juga gw bikin seirit mungkin pake pendekatan **Lazy Loading**. Daripada nge-dump transkrip chat mentah yang panjang dan boros token LLM, script ini sekarang cuma balikin ringkasan bersih dari file `.summary.md` yang relevan, plus `Path` dinamis ke subfolder transkrip mentah di NAS (`daily_sessions/YYYY-MM-DD/`) dan `Links` ke entitas terkait. LLM-nya bisa baca transkrip mentah *on-demand*, cuma kalau butuh detail percakapan yang lebih spesifik.

Dengan cara ini, keuntungan relasi antar dokumen (graf topik) tetap dapet, tapi kodenya enteng, cepet, dan bebas dari bug traversal yang ribet. *Keep it simple!*

### 4. Bonus: kompatibel sama Obsidian vault

Karena konvensi nama file-nya (`YYYY-MM-DD.md`) dan format summary yang baru udah pake YAML frontmatter standar, gw dapet bonus yang nggak disangka: **folder `memory/` bisa langsung di-mount jadi vault Obsidian!**

Gw tinggal nambahin sebaris instruksi di prompt generator summary buat nge-append wikilinks di bagian bawah body markdown:

```markdown
---
# YAML Frontmatter...
---
### Ringkasan Hari Ini
- [Point 1]

---
**🔗 Links:** [[Gading]] · [[Nouverse Core]]
```

Begitu di-mount ke Obsidian di laptop gw, langsung dapet **Graph View**, **Backlinks**, dan **Calendar Heatmap** gratis, tanpa nulis kode visualisasi satu baris pun. RAG-nya seneng karena dapet metadata bersih, gw juga seneng karena bisa browsing riwayat chat Nouva dengan visualisasi graf yang estetik.

Tapi biar grafnya rapi dan nggak jadi benang kusut (*spiderweb*), gw pasang beberapa aturan tambahan:
1. **Related dates nggak dijadiin wikilink:** hubungan antar tanggal (`related_dates`) sengaja **nggak** gw jadiin wikilink visual di body markdown. Cukup disimpen di YAML frontmatter buat dibaca programmatik sama AI. Jadi grafnya bersih dari garis silang-menyilang antar tanggal yang bikin bingung.
2. **Timeline spine:** tiap daily note otomatis nge-link ke catatan hari sebelumnya (misalnya `« [[2026-07-05]] | Timeline Spine`). Ini ngebentuk satu garis lurus kronologis (tulang punggung) dari kiri ke kanan di graf.
3. **Parent link:** file transkrip chat mentah otomatis nge-link ke daily note induknya. Jadi sesi-sesi chat ngorbit rapi ngelilingin bulatan tanggalnya, nggak melayang sendirian sebagai *orphans* (anak yatim).

### Backfill dan rencana migrasi data lama

Tantangan terakhirnya data lama yang keburu diarsipin ke NAS sebelum skema ini aktif. Buat nyelarasinnya, gw bikin script migrasi sekali jalan (`backfill-nas-memories.py`), alurnya:
1.  Nge-scan dan baca daily notes lama dari NAS.
2.  Generate `.summary.md` baru lewat LLM secara bertahap (dikasih jeda `time.sleep(2)` biar LLM-nya nggak mabok).
3.  Simpen file summary-nya di folder lokal `memory/summaries/` (ukurannya kecil banget, jadi nggak ngebebanin disk lokal).
4.  Sync semua summary baru itu ke AnythingLLM.

Jadi, akhirnya gw butuh memory stack eksternal yang canggih dan berbayar? Jawabannya tetap **belum**. Gw masih bisa "ngakalin" pake file markdown lokal, sedikit script Python, dan matematika hybrid scoring sederhana yang disesuaiin sama kebutuhan riil gw, tanpa boros token LLM atau bergantung ke vendor pihak ketiga.

Dari refactoring ini kelihatan, dengan struktur folder markdown yang rapi, YAML frontmatter, sedikit matematika hybrid scoring, dan tool visualisasi markdown standar kayak Obsidian, lu udah bisa bikin sistem memori AI Agent yang pinter, cepet, dan 100% punya lu sendiri.
