Kalau lu sering ngoprek atau pake coding agent yang punya akses terminal (misalnya tool `exec`), lu mungkin pernah ngalamin ini: awalnya agent-nya nurut dan enak diajak mikir, tapi begitu masuk turn ke-20 atau ke-30 mendadak halu, ngulang-ngulang jawaban, atau langsung error `context length exceeded`.

Penyebabnya hampir selalu di manajemen I/O tool yang berantakan. Model LLM-nya sendiri jarang jadi masalah.

Cukup satu perintah terminal yang output-nya nggak kekontrol, misalnya `docker logs`, `git diff` di monorepo, atau build script yang nge-dump stack trace ribuan baris. Ribuan baris teks mentah itu langsung banjir ke context window. Sekali log 4 MB sampai 6 MB masuk mentah-mentah ke payload prompt, efeknya beruntun:
1. Context window langsung mentok.
2. Token input di tiap turn berikutnya bengkak parah (biaya sama latency ikut naik).
3. Model kena *attention drift*. Instruksi penting dan konteks kerjaan yang dibahas di awal sesi tenggelam ketutup tumpukan log terminal yang sebenernya nggak perlu dibaca semua.

Waktu gw bangun **[Nouride](https://nouride.com)** (daemon multi-agent ringan buat kebutuhan homelab), masalah ini jadi prioritas awal yang harus beres. Gw butuh agent kayak Nouva bisa nemenin ngoding sampai puluhan, bahkan ratusan turn, tanpa mogok di tengah jalan.

Ini beberapa cara yang sempet gw coba, plus solusi yang akhirnya gw pake: **Tool Output Spilling**.

---

### Yang udah gw coba dan kurang pas

Sebelum nemu pola yang enak, gw sempet nyoba beberapa cara umum yang ternyata nyusahin pas dipake kerja.

#### 1. Nitip aturan di system prompt
Awalnya gw kira cukup dikasih instruksi di prompt: *"Kalau output terminal kira-kira bakal panjang, redirect ke file ya, terus kasih tahu path-nya aja."*

Ternyata nggak jalan konsisten. Model LLM nggak bisa tahu seberapa panjang output sebuah program sebelum program itu dijalanin. Pas manggil `journalctl` atau `npm test`, model nggak bisa nebak hasilnya 5 baris atau 10.000 baris. Nyerahin kontrol alokasi memori ke feeling model sebelum perintahnya jalan itu rapuh banget.

#### 2. Truncation kasar (potong depan)
Abis itu gw coba pasang limit karakter di backend. Kalau output-nya lewat batas tertentu, dipotong, ambil 2.000 karakter pertama.

Ini malah bikin masalah baru. Di log eksekusi software, sinyal paling penting hampir selalu ada di ujung akhir (*tail*): baris error terakhir, summary compiler, atau exit code failure. Kalau yang diambil cuma bagian depan (*head*), agent cuma ngeliat log inisialisasi yang sukses, terus nyimpulin prosesnya lancar. Padahal aslinya crash di baris ke-5.000.

#### 3. Marker "jalanin lagi kalau butuh"
Ada juga pola agent yang cuma ngasih teks pendek: `[output 5MB dipotong, jalankan lagi perintahnya kalau mau lihat detail]`.

Ini nggak efisien kalau perintahnya proses compile atau test suite yang makan waktu 2 menit. Masa agent harus nunggu 2 menit lagi cuma buat ngintip baris tengah yang tadi nggak kebaca?

---

### Solusinya: spilling ke filesystem

Akhirnya gw adaptasi konsep klasik dari sistem operasi: **memory spilling / paging to disk**. Kalau memori cepat (RAM) terbatas, OS nge-swap halaman memori yang belum kepake ke disk, daripada langsung matiin prosesnya.

Di Nouride, harness daemon duduk di tengah, antara hasil eksekusi tool dan payload prompt yang dikirim ke LLM. Alurnya deterministik.

#### 1. Capping berdasarkan budget turn
Satu hasil tool call nggak boleh ngabisin context window. Di Nouride, satu tool result dijatah maksimal **25% dari total conversation budget** (dengan floor 2.000 token). Jadi kalau agent manggil 3 atau 4 tool sekaligus dalam satu turn, masih ada sisa ruang 50% buat prompt persona, memory, dan chat history.

#### 2. Tulis output utuh ke disk
Kalau panjang tool result-nya lewat batas budget:
- Harness langsung nulis teks utuhnya secara atomic ke disk, di path `$DATA_DIR/tool-output/<session_id>/<call_id>.txt`.
- File-nya langsung dikunci pake permission `0600` (biar nggak bocor kalau isinya ada log environment variable atau secret).
- Folder spill ini otomatis masuk whitelist path sandbox read-only si agent, jadi agent bisa baca file itu pas butuh.

#### 3. Kirim excerpt terstruktur (head & tail)
LLM cuma nerima excerpt ringkas dengan pembagian yang terukur:
- **Head (65%):** bagian awal log, biar model paham parameter inisialisasi dan konfigurasi yang jalan.
- **Tail (35%):** bagian akhir log, biar model langsung baca summary status atau pesan error fatal.
- **Metadata:** jumlah baris dan ukuran asli (KB), plus berapa baris di tengah yang disembunyiin.
- **Pointer path:** lokasi file fisik di disk, lengkap sama petunjuknya: *"Open it with `read` and an offset, or narrow it with `grep`."*

Format yang diterima agent kayak gini:

```text
[output too large for the context: 14,200 lines, ~2,840KB.
The first 65 and last 35 lines are below; 14,100 in the middle are not.]
Full output: /srv/nouride/.nouride/data/tool-output/s_019/call_exec_42.txt
Open it with `read` and an offset, or narrow it with `grep`; it is a normal file and it is readable.

... (baris awal perintah) ...

... (baris akhir / exit error) ...
```

---

### Hasilnya di lapangan

Pola spilling ini langsung beresin beberapa masalah teknis:

1. **Sinyal error tetap utuh.** Karena bagian tail selalu ikut, agent langsung tahu akar masalahnya tanpa nebak-nebak atau halu.
2. **Siap diinvestigasi kapan aja.** Kalau agent butuh ngecek stack trace tertentu di tengah log, dia nggak perlu jalanin ulang command yang berat. Tinggal panggil tool `grep` atau `read` pake offset, langsung ke path file spill-nya.
3. **Ukuran context stabil.** Pemakaian token per turn tetap ramping dan konsisten, dari turn pertama sampai ratusan turn berikutnya.
4. **Lifecycle otomatis.** File spill diurus otomatis berdasarkan timestamp sesi chat. Begitu sesinya udah lewat beberapa hari, file-nya dibersihin sama daemon.

---

### Jadi gini

Agent AI yang bisa diandelin di sesi panjang butuh disiplin kontrol I/O di level runtime harness. Log yang gede dialirin ke filesystem, LLM cuma disuapin ringkasan terstruktur plus pointer ke file-nya. Dengan begitu model tetap fokus ke task utama, dan context window-nya nggak kebebanan.
