Di tulisan sebelumnya ([Part 2](/id/blog/membangun-agent-memory-bebas-vendor)), gw udah cerita panjang lebar soal teori *Hybrid Scoring* dan *1-Hop Related Dates Expansion* buat nyederhanain relasi memori asisten AI gw, **Nouva**. Di atas kertas, konsepnya kelihatan cantik banget.

Tapi pas masuk implementasi beneran di homelab, gw sadar AnythingLLM kayaknya nggak begitu berguna deh.

Akhirnya gw cabut AnythingLLM dari arsitektur memori gw, terus bangun **Nouva Memory Engine** yang ramping pake **FastMCP (Python)**. Engine ini dicolok langsung ke Postgres + `pgvector`, plus database relasional biasa buat analisis yang deterministik.

Ini arsitekturnya, sama lika-liku implementasinya.

---

### Arsitektur baru: Dual-Lane Memory Engine

Sebelum masuk detail kode, ini gambaran umum alur memori Nouva yang baru:

![Nouva Memory Engine Architecture](/media/blog/membangun-agent-memory-part-3/diagram.svg)

Intinya ada di pemisahan jalur pencarian berdasarkan tipe pertanyaan yang masuk (Dual-Lane). Jalur semantik (RAG) sama jalur analisis kuantitatif (SQL) nggak bisa dicampur aduk kalau lu mau hasil yang akurat dan hemat token.

Di sistem ini, data memori dibagi jadi dua status:
1. **Active Memory (lokal)**: nyimpen data yang lagi jalan atau baru kejadian hari ini (kayak transkrip chat aktif harian dan catatan harian yang belum kelar). Data ini disimpen langsung di server lokal agent gw (`active_memory_dir`) biar nulisnya cepet.
2. **Archived Memory (NAS)**: abis lewat *grace period* (misalnya H-1), pipeline otomatis mindahin data yang udah final (transkrip mentah, summary harian, dan indeks) ke storage terpisah di NAS (`archived_memory_dir`), permanen dan read-only. Jadi SSD di server agent gw tetap lega.

### 1. Pensiunin AnythingLLM, pindah ke FastMCP

Awalnya AnythingLLM kerasa ngebantu banget, soalnya dia nyediain API instan buat ngurus dokumen dan vector database. Tapi pas dipikir-pikir lagi, AnythingLLM itu *bloated* buat asisten pribadi yang jalan di homelab. Dia makan RAM dan CPU lumayan di cluster K3s gw, padahal yang gw butuhin cuma:
1. Nyimpen dokumen markdown (`MEMORY.md`, index harian).
2. Dapetin embedding vector-nya.
3. Jalanin query cosine distance.

Jadi AnythingLLM gw decommission permanen. Container-nya gw matiin, volume di server gw hapus, ingress routing-nya gw cabut dari manifes Kubernetes.

Gantinya, gw bikin **Unified Memory Engine** berbasis **FastMCP (Python)**. Kenapa MCP (Model Context Protocol)? Soalnya protokol ini sekarang udah jadi standar industri yang didukung banyak AI Agent client (kayak OpenClaw, Cursor, Zed, dll.). Cukup bikin server MCP sekali, memori ini bisa lu colok ke editor kode, asisten Telegram, atau CLI agent mana aja, tanpa bikin API wrapper baru.

### 2. Dari Zed Editor langsung ke server (lifecycle memori)

Gimana caranya satu interaksi bisa jadi memori? Prosesnya mulai langsung dari workspace ngoding atau chat harian.

Contohnya, pas gw lagi ngoding di **Zed Editor** dan minta asisten AI nyimpen sesi diskusi yang penting, asistennya bakal manggil tool `session_write` (tool FastMCP). Tool ini langsung ngerekam jalannya obrolan, ngemasnya jadi JSON terstruktur, terus nyimpen sebagai file transkrip mentah berformat Markdown di server agent gw:

![Menyimpan Sesi Diskusi dari Zed Editor](/media/blog/membangun-agent-memory-part-3/store.png)

File transkrip yang baru disimpen ini (`2026-07-19-1037.md`) nangkring di server agent gw (`agent-host` di Proxmox) dan langsung dikaitin ke tanggal induknya (`Parent Day: [[2026-07-19]]`):

![Transkrip Tersimpan di Server Agent](/media/blog/membangun-agent-memory-part-3/memory-md.png)

File-file transkrip mentah ini sengaja ditaruh di active storage dulu (server agent gw, bukan NAS) selama grace period H-1. Abis itu baru di-ingest, dibikinin summary, di-index secara semantik, dan diarsipin permanen ke NAS sama pipeline sinkronisasi harian.

### 3. Dual-Lane Memory: RAG semantik vs SQL analytics yang deterministik

Kesalahan paling gede yang sering kelupaan pas orang bikin RAG: maksain pencarian semantik buat pertanyaan kuantitatif.

Misalnya lu nanya ke AI: *"Berapa persen tingkat produktivitas gw di bulan Juli ini?"*

Kalau pake RAG semantik biasa, LLM bakal nyari dokumen yang secara kosinus mirip sama kata "produktivitas Juli". Dia narik 2 atau 3 summary harian acak, terus nyoba "ngarang" persentase dari dokumen yang terbatas itu. Hasilnya **pasti salah atau ngaco.**

Buat beresin ini, gw bagi pemrosesan memori jadi dua jalur (*Dual-Lane*).

#### Lane 1: Semantic Recall (pgvector)
Ini jalur RAG yang biasa. Data dari file markdown utama (`MEMORY.md`, `MEMORY_INDEX.md`) dipotong jadi chunks, di-embed pake model `bge-m3` secara lokal, terus disimpen ke tabel `memory_vectors` di PostgreSQL yang pake ekstensi `pgvector`.
*   **Gunanya:** jawab pertanyaan berbasis konteks, misalnya *"Gimana setup boot order server homelab kemarin?"* atau *"Apa kesepakatan gw sama Kak Rina soal reminder sahur?"*

#### Lane 2: Deterministic Analytics (Postgres SQL)
Tiap kali script sinkronisasi harian (`auto_sync.py`) jalan, dia nggak cuma bikin file markdown summary. Dia juga nge-parse YAML frontmatter di summary itu (kayak `mood`, `importance`, `projects`, `technologies`, `date`) dan nyimpennya sebagai baris data (SQL rows) di tabel `daily_summaries` di PostgreSQL.
*   **Gunanya:** jawab pertanyaan agregat atau tren secara deterministik, misalnya *"Berapa kali gw ngoding pake Next.js bulan ini?"* atau *"Berapa persen hari produktif gw di bulan Juni?"*

Kenapa Postgres? Soalnya perjalanan spiritual tiap developer ujung-ujungnya selalu nyampe di satu kesimpulan: **Just Use Postgres.**

![Just Use Postgres Meme](/media/blog/membangun-agent-memory-part-3/just-use-postgres.jpg)

Daripada pusing deploy database time-series khusus, graph database yang aneh-aneh, atau document store terpisah cuma buat nyimpen summary personal, Postgres plus `pgvector` (buat Lane 1) dan tabel relasional biasa (buat Lane 2) udah lebih dari cukup buat ngurus semuanya sendirian.

Pas asisten AI dapet pertanyaan kuantitatif, dia nggak jalanin vector search. Dia nge-parse query-nya jadi parameter terstruktur (misalnya `start_date="2026-07-01", end_date="2026-07-19", intent="mood_timeseries"`) lewat tool MCP `memory_analyze`, terus jalanin query SQL agregasi langsung ke database.

Jadi AI-nya nggak cuma bisa recall ingatan secara semantik. Dia juga bisa ngitung agregasi data dan tren 100% presisi, kayak database analitik:

![Analisis Mood dan Produktivitas Menggunakan SQL Lane](/media/blog/membangun-agent-memory-part-3/memory-analyze.png)

Angka di atas murni ditarik pake query SQL agregasi. Cepet, akurat, dan nggak buang-buang token LLM buat baca ratusan baris transkrip obrolan.

### 4. Struktur data: Implicit Temporal Graph

Mungkin ada yang penasaran, *"Kalau nggak pake database graf fisik kayak Neo4j, gimana caranya nyambungin ingatan yang nyambung antar hari (temporal relationship)?"*

Jawabannya, struktur graf waktunya disimulasiin secara implisit (**Implicit Temporal Graph**) langsung di atas flat Markdown dan PostgreSQL biasa.

Di sistem ini, struktur datanya kayak gini:
*   **Node (titik)**: entitas tanggal yang unik (misalnya dokumen harian `2026-07-08`).
*   **Edge (garis hubung)**: array `related_dates` di dalam YAML metadata summary.

Ini graph view memori Nouva yang kebentuk otomatis di Obsidian:

![Obsidian Memory Graph View](/media/blog/membangun-agent-memory-part-3/obsidian-graph.png)

Contoh nyatanya, ini potongan metadata YAML dari file `.summary.md` yang disimpen di NAS:

```yaml
schema_version: 1
date: 2026-06-24
people:
- Gading
- Kak Rina
projects:
- Homelab
tags:
- anythingllm-migration
- proxmox-config
technologies:
- Docker
- Terraform
- PostgreSQL
importance: 7
mood: reflective
related_dates:
- '2026-06-23'
- '2026-06-28'
```

Secara logika, ini graf temporal, karena dia nyambungin entitas atau dokumen antar tanggal. Tapi secara fisik, disimpennya sebagai data relasional biasa.

Sifat datanya juga efisien:
1. **Immutable historical logs**: data harian yang udah lewat grace period (H-1) sifatnya read-only dan disimpen di NAS.
2. **Declarative relationships**: hubungan antar hari dideklarasiin secara programmatik pas sync, bukan dihitung dinamis pas runtime query.
3. **Decayed traversal**: pas pencarian semantik (RAG), query engine-nya ngelakuin *1-hop expansion* ke tanggal yang ada di `related_dates`, dengan skor semantiknya dipotong 30% pake rumus peluruhan:

   $$S_{\text{decayed}} = S_{\text{parent}} \times 0.7$$

   $S_{\text{parent}}$ itu skor semantik asli dari tanggal induk yang ketemu lewat RAG. Potongan ini jadi penanda kalau tanggal hasil ekspansi itu informasi sekunder, konteks pendukung aja.

Dengan cara ini, keuntungan Graph/Temporal traversal tetap kedapet, tanpa overhead resource dan ribetnya database graf fisik.

---

### 5. Alur kerja sync pipeline (`auto_sync.py`)

Terus gimana semua data ini tetap sinkron? Gw punya cron job background (`auto_sync.py`) yang jalan otomatis tiap hari, alurnya gini:

1.  **Reconcile & summarize:** baca transkrip chat mentah hari sebelumnya yang masih aktif di host lokal, terus nyuruh LLM lokal bikin summary ringkas format `.summary.md`, lengkap sama YAML frontmatter terstruktur.
2.  **Archive ke NAS:** mindahin file transkrip chat mentah yang asli ke subfolder NAS (`daily_sessions/YYYY-MM-DD/`), biar SSD di host asisten tetap lega.
3.  **Database sync:**
    *   Baca YAML frontmatter dari summary baru, terus masukin ke tabel `daily_summaries` di PostgreSQL (Lane 2).
    *   Update file indeks `MEMORY_INDEX.md`, potong jadi chunks, bikin embedding-nya, terus update tabel `memory_vectors` (Lane 1).

### Hasilnya

Pindah ke **Unified Memory Engine** berbasis FastMCP dan misahin alur pencarian memori jadi **Dual-Lane (Semantic vs. SQL Analytics)** kebukti motong pemakaian resource homelab lumayan banyak. Untung paling gedenya di portabilitas: sekarang gw punya memory service sendiri yang terstandar, yang bisa langsung dicolok dan diakses agent mana aja yang dukung protokol MCP.

Dengan arsitektur ini, asisten AI gw nggak cuma "inget" obrolan masa lalu secara semantik (recall history chat). Dia juga bisa analisis, ngitung agregasi data terstruktur dengan presisi, dan ngelacak tren kebiasaan, produktivitas, sampai kendala teknis harian gw dengan akurat.
