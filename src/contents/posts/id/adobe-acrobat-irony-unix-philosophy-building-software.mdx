Beberapa hari lalu linimasa X gue rame gara-gara satu tweet singkat tapi nusuk dari [@Trish0x2A](https://x.com/trish0x2a/status/2103759408316752027?s=46):

> *"It's honestly embarrassing that Chrome accidentally became the best PDF viewer while Adobe spent decades making Acrobat slower and more bloated."*

![Tweet dari @Trish0x2A soal Chrome vs Adobe Acrobat](/media/blog/adobe-acrobat-irony-unix-philosophy-building-software/tweet-trish.jpg)

Gue langsung ketawa getir pas baca ini. Kenapa? Karena ini bukan cuma soal Adobe, tapi soal penyakit menahun yang menjangkiti hampir semua software komersial di dunia industri kita: **kutukan feature creep**.

Pikirin ironinya: Adobe itu perusahaan yang **menemukan format PDF** pada tahun 1993. Mereka yang nulis standarnya, mereka yang punya ekosistemnya. Tapi hari ini, kalau lu cuma mau baca PDF struk belanjaan atau dokumen dua halaman, buka Adobe Acrobat rasanya kayak mau nerbangin roket ke Mars. 

Laptop mendadak panas, loading screen muter, puluhan background process ikutan jalan (mulai dari Adobe Creative Cloud, Core Sync, IPC Broker, Genuine Service, sampai crash reporter). Belum lagi lu bakal disapa pop-up tawaran langganan cloud storage, e-signature workflow, dan belakangan ini: tombol AI Assistant buat ngerangkum PDF. 

Padahal lu cuma mau satu hal sederhana: **baca dokumen**.

Lalu datanglah Google Chrome. Developer Chromium awalnya cuma butuh komponen kecil biar browser bisa ngerender PDF langsung di tab tanpa perlu download file dulu ke desktop. Gak banyak gaya: render halaman, scroll atas-bawah, zoom in/out, tombol print. Selesai. Hasilnya? Tanpa sengaja, Chrome jadi default PDF viewer favorit miliaran manusia di bumi karena kebuka dalam hitungan 0.1 detik.

Di titik ini, kita harus berhenti sejenak dan nanya: *Kenapa software yang awalnya bagus hampir selalu berakhir jadi bloatware yang nyusahin?*

## Anatomi Penyakit: Kenapa Software Selalu Gemuk?

Developer yang bikin software bloated itu bukan orang bodoh. Masalahnya bukan di skill koding, tapi di insentif sistemik.

1. **Jebakan "Value-Add" Setiap Kuartal**  
   Perusahaan teknologi dituntut terus tumbuh. Tim produk dituntut punya pencapaian baru di review kuartalan. Kalau lu bilang ke manajemen, *"Kuartal ini tim kami gak nambah fitur apa-apa, kami cuma bikin core engine 10% lebih stabil dan hemat memori,"* lu bakal dianggap santai-santai. Tapi kalau lu bilang, *"Kami baru rilis integrasi cloud storage, digital signature, dan AI copilot di dalam PDF reader,"* lu dapet tepuk tangan. Fitur baru = tanda ada kerjaan.

2. **Takut Terlihat "Terlalu Sederhana"**  
   Ada persepsi aneh bahwa software berbayar harus keliatan kompleks biar kerasa harganya. Kalau cuma ada satu jendela putih polos buat baca teks, user (terutama level enterprise procurement) bakal nanya: *"Ngapain bayar mahal kalau tampilannya cuma begini?"* Akhirnya tombol-tombol baru dipaksakan masuk.

3. **Gagal Bedain Core Feature vs Peripheral Plugin**  
   Semua fitur dijejalkan ke dalam satu binary utama. Fitur edit teks, kompresi gambar, form submission, OCR, OCR cloud sync, token analytics—semuanya jalan barengan di thread yang sama.

Hasil akhirnya adalah monster monolitik yang lambat, rakus RAM, dan rapuh.

## Obat Penawar dari Tahun 1970-an: Filosofi Unix

Jauh sebelum kita ribut-ribut soal microservices atau container, Doug McIlroy dan Ken Thompson di Bell Labs udah ngerumusin aturan main yang sampai sekarang belum ada tandingannya:

> 1. *Make each program do one thing well.* Untuk ngerjain tugas baru, lebih baik bikin program baru daripada nambahin fitur rumit ke program lama.  
> 2. *Expect the output of every program to become the input to another, as yet unknown, program.*  
> 3. *Write programs to handle text streams, because that is a universal interface.*

Filosofi Unix ini sering disalahartikan sebagai "bikin program kecil yang gak ada fiturnya". Bukan itu maksudnya. Intinya adalah **modularitas dan isolasi tanggung jawab**.

Kalau lu butuh baca PDF, bikin reader yang fokus render halaman dengan cepat dan benar. Kalau user butuh tanda tangan digital, jangan dijejalin ke core reader; bikin tool terpisah atau plugin terisolasi yang bisa dipanggil kalau memang dibutuhkan.

## Skala Enterprise Lewat Pola "Fleet", Bukan Monolith Gemuk

Banyak orang skeptis: *"Ah, filosofi Unix kan cuma cocok buat CLI tools jadul. Kalau di skala enterprise yang butuh jutaan user dan compliance ribet, mana bisa?"*

Justru sebaliknya. Software infrastruktur paling sukses di era modern semuanya dibangun di atas filosofi ini:

### 1. Docker Engine vs Kubernetes
Docker Engine gak pernah berusaha jadi orchestration cluster raksasa di satu binary. Docker fokus jadi runtime container di satu mesin lokal: build image, run container, expose port. Selesai. 

Begitu kebutuhan skala naik jadi ribuan mesin, solusinya bukan bikin Docker Engine makin bengkak dan monolitik, tapi dibikin layer terpisah di atasnya: **Kubernetes**. Docker tetap kecil dan hening di level worker node, sementara urusan scheduling dan clustering dipegang sistem orkestrasi di atasnya.

### 2. Prometheus vs Thanos / Cortex
Prometheus itu single-node Time Series Database (TSDB). Dia gak punya clustering built-in, gak punya distributed storage bawaan. Desainnya sengaja dibuat sesederhana mungkin biar scraping metrik gak pernah down pas server lagi crash.

Pas perusahaan butuh retensi data multi-tahun dan query global lintas ratusan cluster, apa Prometheus di-rewrite jadi database raksasa? Enggak. Arsitekturnya tetap single-node, lalu di atasnya dipasang **Thanos** atau **Cortex** buat narik data secara federasi.

### 3. Grafana Agent vs Grafana Cloud
Grafana Agent di server lokal cuma tugasnya ngumpulin telemetry dan forward ke tujuan. Dia gak mikirin visualisasi dashboard, gak mikirin alert routing kompleks. Semuanya dipecah jadi komponen yang jelas batas tanggung jawabnya.

Pola ini dikenal sebagai **Shared-Nothing Architecture** atau **Horizontal Fleet**: daripada bikin satu sistem raksasa yang rapuh dan ribet, kita perbanyak instansi-instansi kecil yang mandiri.

## Bagaimana Kami Menerapkannya di Nouride

Waktu gue merancang [Nouride](https://nouride.com) (engine multi-agent AI daemon yang jalan di homelab dan server kami), godaan buat bikin dia jadi *"All-in-One Multi-Tenant Enterprise AI Platform"* itu gede banget. 

Gampang banget buat mabok teori: pasang Postgres cluster, tambahin vector database eksternal macam Qdrant atau Milvus, bikin multi-tenant logic dengan puluhan relasi tabel, dan kasih embel-embel "enterprise ready".

Tapi gue tolak semua itu. Kami milih jalan Unix:

- **Engine-nya Tetap Kecil dan Mandiri:**  
  Nouride didesain sebagai *single binary sovereign daemon*. Databasenya embedded SQLite (`nouride.db`), pencarian semantiknya jalan lewat Ollama lokal (`bge-m3`), dan total konsumsi memorinya cuma **~107 MB RAM** saat menjalankan 6 agent dan 10 gateway (Telegram, Discord, WhatsApp) sekaligus.
- **Isolasi Penuh (Zero Blast Radius):**  
  Alih-alih bikin satu database multi-tenant raksasa di mana data antar divisi berisiko bocor, pendekatan kami untuk scaling adalah: **satu tim = satu instance Nouride terpisah**. Tim DevOps punya instance sendiri dengan akses command terminal (`exec`), tim Legal punya instance sendiri yang terkunci tanpa akses shell. Kalau instance tim A bermasalah, tim B gak bakal kena dampak sama sekali.
- **Fleet Manager di Atas, Bukan di Dalam Core:**  
  Kalau nanti satu perusahaan punya 50 tim dan butuh pengelolaan 50 instance Nouride, solusinya bukan merombak core engine Nouride jadi gemuk. Rencana kami adalah membangun layer **Fleet Control Plane** terpisah di atasnya: sebuah dashboard manajemen tipis buat provisioning container, push konfigurasi masal, dan narik centralized audit log.

Engine Nouride tetap setia sebagai alat kerja yang hening, enteng, dan gak serakah resource.

## Disiplin Bilang "Nggak"

Bikin software itu gampang di awal. Yang susah adalah menjaga software tersebut gak berubah jadi sampah yang lambat setelah berumur lima tahun.

Setiap kali ada ide buat nambahin fitur baru, pertanyaan pertama yang harus diajukan seorang engineer bukan *"Bisa gak kita implementasiin ini?"*, melainkan:

> *"Apakah fitur ini merusak esensi utama dari alasan kenapa software ini diciptakan?"*

Adobe Acrobat mungkin udah terlalu jauh tersesat di rimba feature creep dan metrik monetisasi korporat. Tapi buat software-software yang kita bangun hari ini, kita selalu punya pilihan: mau ikut-ikutan jadi monster yang lambat, atau berdiri di atas pundak para perintis Unix dengan menjaga software kita tetap tajam, hening, dan tuntas ngerjain tugas intinya.
