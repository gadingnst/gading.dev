Beberapa waktu lalu gw sempet bahas [kenapa homelab itu penting](/id/blog/kenapa-homelab-penting). Kali ini gw mau cerita lebih detail soal **gimana gw bangun arsitektur homelab yang sekarang**, dari level fisik (*bare metal*) sampai bisa diakses dengan aman dari internet publik.

Banyak orang yang baru mulai homelab langsung hajar deploy semuanya di Kubernetes (K8s), atau kebalikannya, semuanya pake Docker Compose lepasan di VM/LXC terpisah. Gw ambil jalan tengah: orkestrasi **Kubernetes (K3s)** buat aplikasi *stateless*, dan performa *native* **Standalone LXC** buat layanan *stateful* (kayak database dan storage), semuanya jalan di atas satu hypervisor fisik **Proxmox VE**.

---

## 🛠️ Kenapa Proxmox VE?

Buat fondasi paling bawah (*bare metal*), gw install **Proxmox VE**. Kenapa gak langsung install OS Linux biasa (kayak Ubuntu/Debian) terus pasang Docker?

1. **Virtualisasi Type-1 (Native Performance)**: Proxmox jalan langsung di atas hardware, tanpa overhead OS desktop.
2. **Fleksibilitas VM vs LXC**: Gw bisa bikin Virtual Machine (VM) buat OS penuh yang butuh isolasi kernel (kayak node K8s), sekaligus bikin Linux Containers (LXC) yang ringan banget dan hemat RAM buat service sederhana (kayak database).
3. **Backup & Snapshot Terintegrasi**: Sebelum eksperimen aneh-aneh yang bisa ngerusak sistem, tinggal pencet tombol *Snapshot*. Kalau error, tinggal *Rollback* dalam hitungan detik.
4. **Manajemen Resource yang Presisi**: Gw bisa mantau dan ngebatesin CPU, RAM, dan I/O disk tiap container biar gak saling rebutan resource.

---

## ☸️ Kenapa Pakai Kubernetes? Bukannya Overkill?

Jawaban singkatnya: **Iya, buat skala homelab pribadi, Kubernetes itu overkill banget.** 

Ngelola cluster K8s butuh RAM tambahan buat control plane, konfigurasi networking yang ribet, dan kurva belajar yang lumayan curam. Gw juga sama sekali gak ngejar High Availability (HA) atau *failover* canggih lainnya buat sekadar homelab. 

Ada dua alasan kenapa gw tetep nekat pake Kubernetes:

1. **Dynamic Client Provisioning (Multi-Tenancy)**: Gw lagi bangun platform SaaS/multi-tenant, di mana tiap ada client baru daftar, sistem harus otomatis:
   * Bikin instance aplikasi baru yang terisolasi secara resource dan network.
   * Nyiapin database baru sekalian user-nya.
   * Ngatur routing subdomain (SSL/TLS) otomatis.
   
   Kalau pake Docker Compose lepasan, backend gw harus SSH manual ke server, nulis file compose dinamis, terus jalanin perintah shell. Ini gak aman dan rawan error (*race condition*). Dengan Kubernetes, backend gw cukup nembak **Kube API** secara deklaratif: *"Tolong buatin Namespace baru, buat Deployment ini, dan pasang IngressRoute ini."* Sisanya Kubernetes yang urus. Buat gw, K8s bukan sekadar alat *deploy*, tapi *system engine* buat otomatisasi infrastruktur.

2. **Hands-on Learning (Belajar Praktis)**: Baca dokumentasi Kubernetes itu satu hal, ngelolanya langsung di mesin fisik (*bare metal*) itu beda cerita. Homelab ini tempat main gw buat praktekin konsep *cloud-native* beneran: mulai dari *networking*, *storage provisioning*, *secrets management*, sampai *debugging* pod yang gagal di level OS. Ini cara paling enak buat belajar dan ngerasain *pain points* yang biasa dihadepin tim DevOps di dunia nyata, bukan cuma teori di atas kertas.

## 🚀 Kenapa K3s, Bukan K8s Standar (Kubeadm)?

Walaupun butuh Kubernetes, gw gak pake distribusi K8s standar (kayak *kubeadm*). Di homelab yang RAM-nya berharga banget, **K3s (dari Rancher)** jauh lebih masuk akal.

1. **Ringan Banget**: K3s dikemas jadi satu file binary kecil dan cuma makan RAM sekitar 512MB per node (bandingin sama K8s standar yang bisa makan RAM bergiga-giga cuma buat control plane).
2. **Resource-Efficient**: K3s ngebuang semua provider cloud bawaan (kayak integrasi AWS/GCP) yang gak kepake di homelab, dan ngeganti database internal etcd pake SQLite (atau Postgres eksternal) yang jauh lebih ringan.
3. **Kompatibilitas 100%**: Walaupun ringan, K3s tetep kompatibel penuh sama API Kubernetes standar. Semua manifest YAML Kube biasa bisa langsung jalan.
4. **Bawaan Traefik & Local Storage**: K3s udah bawa Traefik sebagai Ingress Controller bawaan dan Local Path Provisioner buat storage, jadi gak perlu install manual dari nol.

## 🌐 Alur Trafik: Dari Internet ke Pod Aplikasi (Public Access)

Gimana caranya request dari browser user di internet bisa sampai ke aplikasi di dalam cluster Kube tanpa harus buka port (port forwarding) di router ISP?

Ini jalurnya:

1. **Cloudflare Edge (DNS & SSL)**
   User buka `app.mycloud.dev`. Request ini pertama kali diterima server Cloudflare terdekat. Cloudflare ngurus SSL/TLS handshake otomatis di edge mereka.
2. **Cloudflare Tunnel (`cloudflared`)**
   Di dalam cluster Kubernetes, gw jalanin deployment **Cloudflare Tunnel (`cloudflared`)** sebagai Pod. Pod ini bikin koneksi outbound yang aman (tunnel) ke Cloudflare Edge. Karena koneksinya outbound, gak perlu buka port masuk di firewall lokal.
3. **Traefik Ingress Controller**
   Begitu request lewat tunnel, Cloudflare nerusin ke Pod `cloudflared`. Pod ini terus ngelempar trafiknya ke internal Service punya **Traefik Ingress Controller** (yang jadi reverse proxy utama di dalam cluster).
4. **Ingress Routing**
   Traefik baca konfigurasi `Ingress` atau `IngressRoute` yang terdaftar, terus nyocokin rule: *"Kalau host-nya `app.mycloud.dev`, arahin trafik ke Service `core-backend-service` di port `9000`"*.
5. **Kube Service & Pod**
   Trafiknya akhirnya sampai ke Pod aplikasi tujuan dengan aman dan latensi minimal.

## 🔀 Komunikasi Keluar Cluster: Mengakses Standalone LXC

Salah satu tantangan arsitektur ini: **gimana pod di dalam Kubernetes bisa ngakses database atau service staging yang ada di luar cluster K8s (di LXC standalone)?**

Kubernetes punya fitur bawaan yang rapi buat ini, tanpa perlu hardcode IP fisik di kode aplikasi:

### 1. K8s Service Tanpa Selector
Biasanya Service di K8s ngebagi trafik ke Pod berdasarkan label selector. Tapi lu bisa bikin Service **tanpa selector**:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: db-cluster-svc
  namespace: default
spec:
  ports:
    - protocol: TCP
      port: 5432
      targetPort: 5432
```

### 2. K8s Endpoints Manual
Karena Service di atas gak punya selector, Kube gak bakal bikin endpoint otomatis. Endpoint-nya harus didefinisiin manual biar ngarah ke IP fisik LXC standalone (misalnya `db-cluster` di IP `192.168.1.103`):

```yaml
apiVersion: v1
kind: Endpoints
metadata:
  name: db-cluster-svc
  namespace: default
subsets:
  - addresses:
      - ip: 192.168.1.103
    ports:
      - port: 5432
```

Dengan cara ini, aplikasi di dalam cluster Kube cukup nembak host internal `db-cluster-svc.default.svc.cluster.local:5432`. Kalau suatu hari IP database fisiknya berubah, tinggal update file konfigurasi `Endpoints` ini aja, kode aplikasi gak perlu disentuh.

## ⚙️ Dynamic Provisioning: Otomatisasi Client Pod

Buat SaaS atau aplikasi multi-tenant, instance aplikasi baru harus dibikin dinamis tiap ada client baru daftar. Dengan arsitektur ini, alurnya jadi rapi banget:

1. **Request Langganan**
   User daftar, dan backend (`core-backend`) nerima request-nya.
2. **Database Provisioning**
   Backend ngehubungin `db-host` lewat kode buat bikin database dan user terisolasi khusus buat client itu:
   * **Database Name**: `pod_db_<product_name>_<workspace_id>` (e.g., `pod_db_service_clientx`)
   * **Database User**: `pod_user_<product_name>_<workspace_id>` (e.g., `pod_user_service_clientx`)
3. **K8s API Call**
   Backend ngehubungin Kubernetes API Server lewat internal domain **`k8s-api.mycloud.dev`** buat bikin resource baru:
   * Bikin **Namespace** terisolasi: `client-pod-<product_name>-<workspace_id>` (e.g., `client-pod-service-clientx`).
   * Bikin **Secret** yang isinya kredensial database unik punya client itu.
   * Bikin **Deployment**, **Service**, dan **IngressRoute (Traefik)** khusus buat nge-route subdomain client (`clientx.mycloud.dev`).

### Kenapa Dipisah Per Namespace?
Kalau tiap instance client dipisah ke namespace-nya masing-masing:
* **Isolasi Keamanan Ketat**: Client A gak bakal bisa ngintip atau ngakses resource punya Client B secara internal.
* **Resource Quota**: Pemakaian CPU/RAM per client bisa dibatesin tegas pake Kube `ResourceQuota`.
* **Deprovisioning yang Bersih**: Kalau client berhenti langganan, backend cukup hapus namespace-nya. Kubernetes otomatis bersihin semua resource di dalamnya tanpa nyisain file sampah di server.

## 💡 Hasilnya

Misahin tanggung jawab antara **Kubernetes** (buat aplikasi dinamis dan stateless) dan **LXC Standalone** (buat database dan storage) bikin homelab gw jauh lebih stabil. 

Gw dapet keuntungan orkestrasi dari Kubernetes (auto-healing, scaling yang gampang, dynamic provisioning via API), tanpa ngorbanin performa read-write disk database, yang biasanya lambat kalau dijalanin di storage virtual Kubernetes.

Semua infrastruktur ini didefinisiin pake **Terraform** buat sisi Proxmox-nya, jadi kalau server mati, seluruh homelab ini bisa di-*re-provision* dalam hitungan menit.
