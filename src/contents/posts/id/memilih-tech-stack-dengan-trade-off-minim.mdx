Waktu awal-awal getol ngoding, gw gampang banget kepancing sama apa pun yang lagi rame di timeline. Ada framework baru yang ngeklaim "100x faster than Node", bawaannya pengen langsung rewrite. Liat postingan arsitektur berlapis-lapis lengkap sama diagram kotak-kotaknya, gw langsung ngerasa kode gw amatir kalau nggak pake struktur yang sama.

Terus kena realita production.

Beberapa kali dibangunin jam 2 pagi gara-gara service macet. Muter-muter lewat delapan lapis interface kosong cuma buat nemu satu query SQL. Nunggu build lama cuma buat benerin typo satu baris. Abis ngalamin itu semua, cara pandang gw berubah total.

Sekarang patokan gw simpel: pilih teknologi yang trade-off totalnya paling kecil buat masalah yang lagi diselesaiin, bukan yang paling ekstrem di satu sisi.

---

### Tiga jebakan yang sering bikin repot

Di lapangan, pilihan stack sering ketarik ke salah satu dari tiga sudut ini.

#### 1. Kebablasan ngejar performa

Niatnya bagus: pengen binary kecil dan RAM di bawah 10MB, jadi semuanya ditulis pake Rust atau C++.

Gw nggak anti-Rust, dan nggak benci bahasa low-level. Rust, C++, atau Zig itu juara kalau dipake di tempatnya: core runtime engine, storage engine database, codec video/audio, atau driver OS. Tapi buat aplikasi sehari-hari, automasi, atau backend bisnis, waktu development sama mental overhead-nya sering nggak sebanding sama hasilnya.

Mau nambah satu field di payload JSON aja jadi lama, soalnya harus lolos compile-time check yang ketat. Build-nya lambat. Energi yang harusnya buat mikirin logika produk malah habis buat ngeladenin ritual bahasanya.

#### 2. Kebawa arus tren

Ini biasanya kejadian di project yang arsitekturnya disusun dari apa yang lagi rame bulan ini.

User aktif belum nyampe seratus, tapi storage-nya udah dipecah ke lima tempat: database relasional, vector database, document store, cache layer, sama time-series database. Semuanya jalan di cluster Kubernetes multi-node.

Di kertas sih kelihatan keren. Begitu masuk operasional, ngerawatnya bikin pusing. Sekali ada network partition atau koneksi drop di homelab, waktu lu habis buat mastiin data antar-database nggak belang. Pas ada request gagal di tengah jalan, nyari titik putusnya kayak detektif.

#### 3. Terlalu kaku ngikutin teori buku

Ini kebiasaan ngebungkus kode simpel pake lapisan abstraksi berlebihan, demi ngikutin Clean Architecture kata per kata.

Buat ngambil data user berdasarkan ID doang, alurnya harus lewat Controller, Presenter, UseCaseInterface, UseCaseImpl, RepositoryInterface, RepositoryImpl, DTO, sama Mapper.

Rapi sih di teori, tapi susah ditelusurin. Pas ada bug, lu harus klik berkali-kali lewat interface yang isinya cuma ngoper parameter ke file sebelahnya. Stack trace-nya jadi panjang, penuh wrapper yang nggak ngasih info baru.

### Nyari titik tengah yang masuk akal

Abis beberapa kali kejebak pola-pola tadi, sekarang gw milih opsi yang efisiennya cukup, tapi nggak nambah ribet di operasional.

Ini beberapa keputusan di project gw belakangan ini, termasuk pas nyusun runtime agent.

#### TypeScript di atas Bun

* Gw nggak maksain Rust buat aplikasi yang butuh iterasi cepet. Gw juga nggak pake Python murni, yang startup-nya lambat dan idle memory-nya gampang bengkak di atas 400MB.
* Runtime Bun-nya sendiri udah irit: satu binary yang ringkas, idle memory cuma puluhan MB.
* Kuncinya di disiplin dependency. Kalau aplikasinya dibangun di atas Bun dengan dependency seminimal mungkin (nggak asal pasang ratusan library), performa dan pemakaian resource-nya kerasa hampir setara aplikasi compiled. Bonusnya, feedback loop-nya instan dan ekosistem TypeScript-nya tetep kepake.

#### PostgreSQL plus pgvector

* Gw nggak jalanin vector database terpisah, yang butuh backup, monitoring, dan port sendiri di homelab.
* Cukup satu instance PostgreSQL. Tabel relasional masuk, query analitik jalan, dan semantic search buat retrieval agent ditanganin pgvector. Operasionalnya ringkas, dan Postgres udah teruji puluhan tahun.

#### Arsitektur yang langsung dan secukupnya

* Isolasi dependency cuma gw bikin di bagian yang beneran rawan lock-in, misalnya layer filesystem atau wrapper network.
* Sisanya ditulis sebagai fungsi TypeScript biasa yang langsung ngerjain tugasnya. Batas antar-modul dijaga pake script linting di CI, bukan pake puluhan interface kosong.

---

### Jadi gini

Makin lama ngurusin sistem yang harus nyala terus, gw makin ngehargain yang simpel.

Bahasa low-level tetep punya tempatnya, jadi fondasi engine di balik layar. Tapi buat aplikasi di atasnya, kode yang bagus buat gw itu yang kelar sesuai kebutuhan, gampang dipahamin orang lain (atau diri lu sendiri beberapa bulan lagi), dan jarang bikin panik pas lagi ditinggal tidur.
